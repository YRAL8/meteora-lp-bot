# Правила обновления зависимостей

Бот держит приватный ключ кошелька на той же машине, где исполняет чужой код:
199 пакетов npm и 12 пакетов Python, написанных сотнями посторонних людей.
Взломанная зависимость читает ключ изнутри — фаервол, пароль на SSH-ключе и
белый список адресов против этого не значат ничего.

Это не выдумка. В декабре 2024 в npm вышли версии `1.95.6` и `1.95.7` пакета
`@solana/web3.js` — прямой зависимости этого бота — с кодом, выгребавшим
приватные ключи. Вредонос прожил в реестре около пяти часов и унёс порядка
$160 тысяч. Кто ставил из lock-файла, не пострадал; кто в тот вечер собрал
образ заново, получил закладку.

Отсюда правила ниже. Все они об одном: **что стоит на машине, определяем мы,
а не то, что сегодня оказалось свежим в реестре.**

## 1. Версии прибиты точно

`requirements.txt` — только `==`, включая транзитивные пакеты.
`ts/package-lock.json` — в репозитории, он и есть источник истины для npm.

Диапазоны (`>=`, `^`, `~`) в требованиях запрещены. В `ts/package.json`
диапазоны остались, но на сборку не влияют: `npm ci` смотрит только в
lock-файл.

## 2. Ставим только воспроизводимо

```
npm ci        # да — ставит ровно то, что в lock-файле
npm install   # НЕТ — переписывает lock-файл и может подтянуть новое
```

Python — `pip install -r requirements.txt` с прибитыми версиями.

## 3. Карантин 14 дней

Ничего свежее двух недель не ставится, даже если релиз чинит что-то нужное.
Та закладка в web3.js прожила пять часов; двухнедельная выдержка делает этот
класс атак практически недостижимым, а стоит ноль.

## 4. Обновляемся отдельным заходом

Раз в квартал либо по конкретной причине (уязвимость, нужная правка) — но
**не** попутно с другой работой. Порядок:

1. обновить версии в `requirements.txt` / через `npm install <пакет>@<версия>`;
2. прогнать `python tests/run_tests.py` целиком;
3. отдельный коммит, где нет ничего кроме обновления зависимостей;
4. выкатить и посмотреть журнал бота — не появилось ли нового шума.

Отдельный коммит важен: если после обновления что-то поедет, откатывать надо
обновление, а не рабочую правку, приехавшую вместе с ним.

## 5. Пересборка образа не должна менять пакеты незаметно

Слой `pip install` в `Dockerfile` кэшируется, пока не менялся
`requirements.txt`. Кэш может и промахнуться — например, после `docker builder
prune` или на чистой машине. Поэтому проверка после любой пересборки:

```
docker exec meteora-lp-bot pip freeze | sort > /tmp/pkgs_old.txt
docker run --rm --entrypoint pip <образ> freeze | sort > /tmp/pkgs_new.txt
diff /tmp/pkgs_old.txt /tmp/pkgs_new.txt
```

Различий быть не должно. Есть различия — разбираться до перезапуска, а не после.

## Что сознательно не сделано

- **Хэши артефактов** (`pip install --require-hashes`). Защищают от подмены
  артефакта на стороне PyPI — событие куда более редкое, чем свежий
  отравленный релиз, который уже закрыт пунктом 1. Делать, когда горячая сумма
  дорастёт до трёхзначной.
- **Базовые образы по digest.** `node:20-slim` и `python:3.12-slim` — плавающие
  теги: пересборка на чистой машине возьмёт свежий образ. Прибивать по digest
  тогда же, когда и хэши.

Оба пункта — осознанная отсрочка, а не забывчивость. Пока в кошельке $12,
возня не окупается; при росте суммы вернуться сюда.
